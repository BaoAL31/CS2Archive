# ADR 0003: Edit Timeline LLM Behavior Guidelines

## Context
The Edit Timeline is generated by an LLM that reads the Kill Timeline and assigns POVs to segments. This document defines the system prompt and behavior rules for that LLM.

## Decision
The LLM receives a structured prompt containing:
1. Kill Timeline (all kills with ticks, rounds, attacker/victim, weapons)
2. Player list (all players in demo with steam_ids and names)
3. Match metadata (map, source, demo path)

The LLM outputs a JSON object matching the Edit Timeline schema.

Each per-batch user prompt includes **synthetic few-shot examples** (warmup single segment, live-round multi-POV with omitted trade, one-round-per-segment) with fictional players and steam IDs — not copied from any production match.

## System Prompt

```
You are an expert CS2 highlight reel editor. Your job: watch a match through its Kill Timeline and decide which player's POV tells the best story at each moment.

INPUT:
- Kill Timeline: every kill in order (tick, round, attacker, victim, weapon, headshot, bomb)
- Player list: all players with steam_ids and names

OUTPUT: JSON with segments covering highlight-worthy moments. Multiple POVs per round are allowed; tick ranges may overlap.

RULES:
1. SEGMENT BOUNDARIES align to kill action with lead/tail padding. Do not cross into the next round. Skip the first 24s after round_start (buy/freeze) unless kills occur during that window.
2. SEGMENT TYPES: multi_kill (2+ kills same attacker quick succession), entry (first kill of round), clutch (1vX won), trade (teammate kill within 3s of death), utility (defined by utility usage around kill), default (fallback).
3. POV ASSIGNMENT:
   - multi_kill: attacker POV
   - entry: attacker POV
   - clutch: clutch winner POV (the solo player)
   - trade: trade-killer POV (teammate who got the trade)
   - utility: utility thrower POV
   - default: most recent killer POV
4. ONE ATTACKER PER SEGMENT: different attackers' kills in the same round → separate segments (overlapping tick ranges OK). Example: Player A multi-kill, then ~2-3s later switch to Player B POV for their kills.
5. RECOGNISED PROS (from player_accounts.json) get POV priority when they are the attacker/victim in a segment. Unknown players only get POV if no Recognised Pro is involved.
6. VICTIM POV only for clutches (the clutcher's POV is the story). Never assign victim POV for multi_kill/entry/trade.
7. KILL INDICES: each segment's kill_indices must index into the input Kill Timeline's kills array (0-based).
8. RATIONALE: 1-2 sentence explanation of why this POV and type was chosen.

CONSTRAINTS:
- Output ONLY valid JSON matching the schema.
- No commentary, no markdown fences.
- If uncertain, use "default" type and most recent killer POV.
```

## Schema (JSON Schema)

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "required": ["demo_path", "map", "segments"],
  "properties": {
    "demo_path": { "type": "string" },
    "map": { "type": "string" },
    "segments": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["start_tick", "end_tick", "pov_steam_id", "segment_type", "kill_indices", "rationale"],
        "properties": {
          "start_tick": { "type": "integer", "minimum": 0 },
          "end_tick": { "type": "integer", "minimum": 0 },
          "pov_steam_id": { "type": "string" },
          "segment_type": { "type": "string", "enum": ["multi_kill", "entry", "clutch", "trade", "utility", "default"] },
          "kill_indices": { "type": "array", "items": { "type": "integer", "minimum": 0 } },
          "rationale": { "type": "string", "minLength": 10 }
        }
      }
    }
  }
}
```

## Validation Rules (post-LLM)

1. Segments sorted by start_tick (overlaps allowed; not required to be contiguous)
2. Segment must not cross the next round's start_tick; start_tick is at/after buy-time end (24s) on live rounds unless kills occur during freeze; warmup/knife round 0 starts at round_start (no +24s buy)
3. Every kill_index references a valid kill in Kill Timeline
4. Every pov_steam_id exists in demo player list
5. At least one Recognised Pro POV appears if any Recognised Pro has kills
6. No segment with kill_indices = [] (minimum 1 kill per segment)
7. Not every kill in the Action Timeline must appear in a segment (narrative omissions OK after fix pass)

## Deterministic fix pass (`_fix_edit_timeline`)

Always runs after the LLM merges batches (not only on validation failure). General rules — no match-specific logic:

| Step | Rule |
|------|------|
| Dedupe kills | Each kill_index appears in at most one segment (first segment wins) |
| Recover pro omissions | Auto-insert single-kill segments only for **Recognised Pro** attackers missing from LLM output |
| Merge streak fragments | Adjacent segments, same sole attacker, gap ≤192 ticks (3s) → one multi_kill |
| Split by attacker | One POV per attacker per segment |
| Split by round | One round per segment |
| Consolidate runs | Per round: consecutive attacker runs in kill order → one segment; warmup round → single segment, majority-attacker POV |
| Dedupe segments | Drop segments with identical kill_indices sets |
| Segment types | 2+ kills, single attacker → `multi_kill` |
| Tick anchors | Buy floor (live +1536 ticks); first segment in round starts at play floor; lead/tail padding; min 384 ticks; hard cap `end_tick` before next round_start |
| Handoff | Later segment in same round: start ≤ prior segment's last kill + ~160 ticks (~2.5s) when overlapping POVs |
| POV | Majority attacker in segment |
| Multi-kill window | Drop other players' solo kills whose ticks fall inside a pro's multi-kill tick window (absorb into streak or omit) |
| Post-streak sandwich | Drop other-attacker solo segments sandwiched after a pro 2+ streak before the next highlight in the round |
| Re-anchor | Recompute ticks after structural edits |

Constants (64 tick): `MIN_DURATION_TICKS=384`, `MULTI_KILL_WINDOW_TICKS=192`, `BUY_TIME_TICKS=1536`, `HANDOFF_TICKS=160`, `WARMUP_ROUND=0`.

## Retry Strategy

On validation failure, re-prompt with error details and up to 2 retries (3 attempts total). If all attempts fail validation, or if the LLM call itself fails (API error, network, auth), throw a descriptive error — **no heuristic fallback**. The pipeline stops and requires manual intervention or API key fix.

## LLM Provider

Primary: **Zen API** (opencode.ai/zen) with `mimo-v2.5-free` (fast, zero reasoning overhead).
Fallback: **Zen API** with `deepseek-v4-flash-free` (handles complex contiguity but emits reasoning tokens).
Ultimate fallback: **OpenRouter** with `nvidia/nemotron-3-ultra-550b-a55b:free`.

Requires `ZEN_API_KEY` in `.env` (primary). `OPENROUTER_API_KEY` is optional for ultimate fallback.

### Reasoning Token Behavior

`deepseek-v4-flash-free` emits reasoning tokens before the JSON output via the `model_extra.reasoning_content` field. If `max_tokens` is set too high, the model spends all tokens on reasoning and produces empty `content`. Mitigation:
- Set `temperature=0.0` and `max_tokens=32768` (enough headroom for reasoning + content)
- Use `mimo-v2.5-free` as primary — zero reasoning tokens
- Compress prompt to reduce reasoning burden
